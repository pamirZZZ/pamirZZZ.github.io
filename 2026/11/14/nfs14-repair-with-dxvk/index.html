问题现象与日志分析

11 月 13 日下午，我通过 Steam 启动《Need for Speed: Hot Pursuit》（2010 年原版，AppID 47870，非 Remastered 版本）。进入游戏数分钟后，准备开始比赛时，画面停止响应，随后游戏直接退出到桌面。过程中没有错误弹窗，也没有出现黑屏或“程序已停止工作”等提示。

首先检查 Windows 事件日志。Application 日志中与游戏相关的记录只有一条：

这条记录需要结合其他日志中缺失的信息来判断：

  • 没有 Application Error（事件 1000）或 Application Hang（事件 1002）：系统没有记录常见的应用程序崩溃或无响应事件，也没有提供故障模块和异常代码。
  • System 日志中没有 Display 4101（TDR）或 LiveKernelEvent：没有证据表明显卡驱动发生超时复位；同时也没有 BugCheck 1001 蓝屏记录。
  • 出现 RADAR_PRE_LEAK_WOW64：这是 Windows 资源耗尽检测器（Resource Exhaustion Detector）针对一个 32 位 WOW64 进程生成的资源耗尽预警。

结合文件时间和事件记录，可以整理出以下时间线：

时间（11 月 13 日） 事件
12:22 Steam 安装完成，游戏本体约 8.4 GB
16:28 启动游戏，写入 GAMELOGIC 等资源目录
16:29:38 资源耗尽检测器启动
16:29:42 WER 记录 RADAR_PRE_LEAK_WOW64，对应进程为 NFS11.exe
16:40:27 游戏目录中出现 DXVK 的 d3d9.dll
23:34 再次启动游戏，未复现崩溃；此后日志中也没有新的 NFS11 相关记录

当时的硬件和系统环境如下：

部件 型号 / 参数
机型 Lenovo 21KUA004CD
CPU Intel Core Ultra 5 125H，14 核 18 线程，18 MB L3
核显 Intel Arc Graphics（驱动报告为 Arc Pro Graphics），驱动版本 32.0.101.8805
内存 32 GB DDR5-5600（2×16 GB）
系统 Windows 11，10.0.26300
屏幕 2560×1600 @ 90 Hz

游戏运行时使用 2560×1600 全屏模式。较高的渲染分辨率可能增加图形资源占用，是后续分析中的一个重要条件。

崩溃原因分析

1. NFS11.exe 是未启用 LAA 的 32 位程序

首先检查游戏主程序的 PE 头。结果可以确认程序架构以及是否启用了 Large Address Aware：

输出结果：

0x014C 表示该程序是 x86 32 位应用程序。Characteristics 字段中的 0x0020（Large Address Aware）标志未设置，因此进程没有启用大地址感知。在常规 64 位 Windows 环境下，这类进程的用户态虚拟地址空间上限为 2 GB。这个限制与机器安装了多少物理内存无关。

2. D3D9 资源和驱动开销可能占用进程地址空间

Intel Arc 核显没有独立显存，图形资源主要使用系统内存。对于通过 D3D9 运行的程序，资源管理和驱动实现可能产生额外的进程内存开销，主要包括：

  • Managed Pool 资源：D3D9 的 managed 纹理和缓冲区由运行时管理。系统内存中的资源副本、更新过程中的暂存数据等，可能增加进程的地址空间占用。
  • 驱动进程内开销：着色器编译中间数据、资源上传或回读所需的暂存区，以及命令缓冲等，都可能占用调用进程的虚拟地址空间。
  • 渲染目标与交换链：在 2560×1600、32 位色下，单个全尺寸缓冲区约占 15.6 MB。多个后台缓冲区、深度缓冲区以及 MSAA 资源会进一步增加占用，实际数量取决于具体配置和驱动实现。
  • 游戏自身的流式资源：游戏使用内存映射等方式按需读取 .BNDL 归档文件。映射区域也会占用进程虚拟地址空间，但不等同于文件大小全部常驻物理内存。

这款游戏发布于 2010 年，其开发和测试环境与当前机器存在较大差异。当时常见的显示分辨率和显存容量都低于本机配置。当前使用的 2560×1600 分辨率，相比 1280×1024 的像素数量约为 3.1 倍，可能导致渲染目标和相关资源占用增加。在 32 位进程的地址空间受到限制时，这些额外开销值得重点排查。

3. 地址空间分配失败不一定表现为标准崩溃

当进程可用地址空间不足时，VirtualAlloc 或 D3D9 资源创建操作可能返回失败，例如 E_OUTOFMEMORY 或 D3DERR_OUTOFVIDEOMEMORY。如果游戏没有对这些返回值进行充分处理，可能出现渲染线程停滞、画面冻结，最终进程退出等现象。

这与本次日志情况基本一致：

  • 没有访问违规记录，因此没有常见的 APPCRASH 和故障模块信息；
  • 没有 GPU 超时复位记录，因此没有对应的 TDR 4101 事件；
  • WER 记录了资源耗尽检测器生成的 RADAR_PRE_LEAK_WOW64 事件。

需要注意，当前 WER 报告没有生成 dump（These files may be available here: NULL，Report Status 为 268435456）。因此，以上判断是根据事件签名、时间线、硬件环境和 PE 头信息综合推断的，并非通过调用栈直接确认。它能够解释目前观察到的现象，但还不能视为已经由崩溃转储证实的根因。

可选解决方案

以下方案按照对问题可能产生的影响和实施成本进行比较：

  1. 降低分辨率、关闭抗锯齿或降低纹理质量：可以减少部分图形资源占用，但会牺牲画质。适合作为快速验证手段，未必能解决根本限制。
  2. 启用 4 GB / LAA：修改 PE 头中的 Large Address Aware 标志，使程序在 64 位 Windows 下有机会使用更大的用户态地址空间。该方案需要修改游戏可执行文件，Steam 更新或验证游戏文件时可能覆盖修改；此外，也无法保证旧程序中的所有地址处理逻辑都兼容更大的地址空间。
  3. 更换或回滚 Intel 显卡驱动：不同驱动版本的 D3D9 实现和资源管理方式可能存在差异，但效果不确定，而且可能影响其他应用和游戏。
  4. 增加页面文件或关闭后台程序：关闭后台程序可以减少系统整体资源压力，但增加页面文件不会提高 32 位进程的虚拟地址空间上限。页面文件主要影响系统提交限制，不能直接解决本次怀疑的 2 GB 地址空间限制。
  5. 启用兼容性模式或禁用全屏优化：这些设置主要影响程序兼容性、窗口管理和 DWM 呈现行为，不会改变进程的地址空间上限，因此与当前推测的原因关联较小。
  6. 使用 D3D9On12：通过 D3D12 后端实现 D3D9 接口，有机会绕开部分原生 D3D9 驱动路径。具体效果取决于系统组件和驱动支持情况，排查时也需要额外配置。
  7. 使用 DXVK：将 D3D9 调用转换为 Vulkan，改变原有图形 API 的执行路径。它可以通过应用目录中的 DLL 部署，容易回滚，并提供独立日志用于诊断。

本次最终采用第 7 种方案。降低分辨率虽然可以用于验证资源占用是否相关，但不希望长期降低画质；修改可执行文件则会引入额外的兼容性和维护风险。DXVK 的部署和回滚成本相对较低，也更容易观察运行状态。

选择 DXVK 的原因

选择 DXVK 主要基于以下几点：

  • 部署简单且可逆：将对应架构的 d3d9.dll 放入游戏目录即可，不需要修改游戏 EXE 或系统目录。删除该文件即可恢复原有加载方式。
  • 提供 x86 构建：官方发布包包含 x32 版本。日志中的 Build: x86 表明加载的是 32 位构建，与 NFS11.exe 的架构一致。
  • 日志信息较完整：DXVK 会在游戏目录生成 NFS11_d3d9.log，记录设备信息、驱动版本、内存堆、交换链和着色器缓存等内容，便于确认初始化过程和排查问题。
  • 已有较多实际使用案例：DXVK 常用于在较新的系统和硬件上运行旧版 D3D9 游戏。
  • 可能改善着色器编译造成的卡顿：DXVK 支持磁盘着色器缓存。缓存命中后，可以减少重复编译。本机缓存记录为 640 个 shader，大小约 3.0 MB。

DXVK 的工作原理

1. 通过应用目录中的 d3d9.dll 接管加载

NFS11.exe 启动时需要加载 d3d9.dll。Windows 的 DLL 搜索顺序会优先检查应用程序目录；由于 d3d9.dll 不在系统 KnownDLLs 列表中，放在游戏目录下的同名 DLL 可以优先于系统版本被加载。

我检查了注册表路径 HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs，其中没有与 D3D 相关的条目。

DXVK 的 DLL 在文件属性中使用了 10.0.17763.1 等版本信息，产品名称显示为 Direct3D 9 Runtime。这些元数据并不代表它是微软提供的系统组件；实际加载的是 DXVK 实现的 D3D9 到 Vulkan 翻译层，文件大小约为 7.8 MB。

2. 将 D3D9 调用转换为 Vulkan

游戏调用 CreateDevice、CreateTexture、DrawPrimitive 等 D3D9 接口时，DXVK 会将相关操作转换为 Vulkan 调用，再交由 Intel Vulkan 驱动执行。设备初始化日志如下：

Memory 部分显示了 Vulkan 驱动报告的设备内存堆信息。对于核显，这类 device-local 内存通常对应系统内存中可供 GPU 访问的区域，并不意味着机器上存在同等容量的独立显存。

DXVK 通过 Vulkan 的资源和内存管理机制处理图形资源。与原生 D3D9 路径相比，资源分配、缓存和暂存数据的管理方式会发生变化，因而可能降低原先由 D3D9 运行时和驱动路径产生的部分进程内存开销。不过，Vulkan 资源并非完全不占用进程地址空间；DXVK 自身仍然需要维护对象、句柄、描述符及其他管理数据。

因此，更准确的说法是：DXVK 改变了图形资源的管理路径，可能缓解原生 D3D9 路径下的地址空间压力，而不是简单地将所有纹理副本从 2 GB 地址空间中完全移除。

3. 着色器编译与磁盘缓存

D3D9 游戏运行时会创建和使用大量着色器。DXVK 会将相关着色器代码转换为 Vulkan 使用的形式，并将编译结果写入磁盘缓存。

从日志可以确认，当前交换链使用 2560×1600 分辨率，图像数量为 3，并采用 VK_PRESENT_MODE_FIFO_KHR 呈现模式。全屏切换、垂直同步和帧队列等行为由 DXVK 的呈现层处理，而不是直接沿用原生 D3D9 呈现路径。

这种处理可能用于规避部分旧游戏对显卡型号的硬编码判断，或避免游戏将未识别的 GPU 送入不合适的兼容性分支。该游戏的注册表 3D Data 数据库包含多条显卡记录，说明游戏确实存在基于 GPU 信息进行配置或判断的机制。不过，仅凭这段日志还不能确定游戏具体采用了哪条判断逻辑，也不能据此断言这是本次崩溃的直接原因。

代价与注意事项

DXVK 并不能保证所有 D3D9 游戏都能无问题运行，使用时需要考虑以下情况：

  • 首次启动或首次进入新场景时，可能出现着色器编译卡顿；后续运行会在缓存命中时有所改善。
  • 个别后处理效果或渲染细节可能与原生 D3D9 路径存在差异。
  • DXVK 依赖可用的 Vulkan 驱动。如果显卡驱动或 Vulkan 实现本身存在问题，DXVK 也可能受到影响。
  • 对带有反作弊机制的联机游戏，不应随意替换或注入图形 DLL。DXVK 更适合用于单机旧游戏，使用前应确认游戏及平台规则。

结论

本次问题的主要线索是：NFS11.exe 属于未启用 LAA 的 32 位程序，进程用户态地址空间上限为 2 GB；Windows 同时记录了 RADAR_PRE_LEAK_WOW64 资源耗尽预警。结合高分辨率运行环境和 D3D9 资源管理开销，地址空间不足是一个较合理的解释，但由于没有 dump 或调用栈，目前仍属于基于现有证据的推断。

部署 DXVK 后，游戏在相同机器和分辨率下未再复现崩溃，日志也没有出现新的相关资源耗尽记录。这个结果说明更换 D3D9 到 Vulkan 的执行路径对本机环境有效，但单次前后对比不足以证明原生 D3D9 的某一项具体分配必然导致了崩溃。

对于这类 32 位老游戏，排查时应优先确认进程架构、LAA 标志和系统事件记录，再结合图形 API、驱动及资源占用情况选择兼容方案。DXVK 的优势在于部署简单、容易回滚，并且提供了较好的运行日志，适合作为这类问题的排查和兼容性解决方案。
